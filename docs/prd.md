## 1. 产品定位与目标

### 1.1 产品定位

Kairo 是运行在企业现有 IM 之上的智能助手应用。员工继续通过原有 IM 与 Bot 交流，不要求另行使用一个聊天网站。

Kairo 需要把消息、员工身份、个人记忆、企业知识、文件处理和审批串联起来。Agent、记忆、检索、文档处理等通用能力优先复用现成框架、开源产品和库，不再自行开发一套同类基础设施。

### 1.2 产品目标

| 目标 | 说明 |
| --- | --- |
| 适应真实 IM 对话 | 员工可以分多条消息描述任务，也可以先发文件再补充要求。 |
| 支持多人且保持隔离 | Bot 能持续记住不同员工的信息，不把一个人的私人记忆用于另一个人的回答。 |
| 使用企业知识回答 | 能检索企业资料，依据来源作答，并限制知识访问范围。 |
| 接收与交付文件 | 能处理员工发送的文件，并根据任务返回 PDF、Word、Excel、Markdown 或图片文件。 |
| 支持企业审批 | 需要审批的操作先等待授权；优先考虑通过 IM 完成审批交互。 |
| 可定制 Bot | 支持类似 SOUL.md 的人格与行为配置，并复用现有 Skills / Tools 能力。 |
| 减少自研维护负担 | 自研重点放在 IM 和企业业务衔接上，而不是重写框架、知识库、OCR 或工作流引擎。 |

### 1.3 使用角色

| 角色 | 主要诉求 |
| --- | --- |
| 普通员工 | 在 IM 中提问、上传文件、发起任务、接收结果。 |
| 审批人 | 知道谁申请了什么，准确批准或拒绝对应申请。 |
| 知识维护人员 | 上传、更新、删除企业资料，检查知识检索效果。 |
| 技术维护人员 | 配置 Bot、工具和运行环境，排查消息、任务与审批问题。 |

这些是业务角色，不意味着必须新增四套账号体系或管理页面。

## 2. 已确认的需求与条件

| 项目 | 已确认内容 |
| --- | --- |
| IM 数量 | 只有一个企业 IM，不需要为多个 IM 平台预先建设通用适配框架。 |
| IM 基础能力 | 已有消息监听、消息发送、图片发送、文件发送等接口，当前由 `@kairo/driver` 承担接入职责。 |
| 组织架构 | Driver 提供组织架构相关接口。具体字段、完整性和同步方式仍需验证。 |
| 使用场景 | 企业内多人使用，不是个人助手。 |
| 消息习惯 | 用户可能将一个请求拆成多段发送，段与段之间可能有时间间隔。 |
| 多人记忆 | 必须支持多人记忆，并实现隔离。 |
| 文件输出 | 需要支持 Bot 返回 PDF、Word、Excel、Markdown、图片文件。 |
| 文件输入 | 需要处理用户发送的文件，解析与任务衔接方式需要设计。 |
| Agent 方向 | 用户倾向于使用 Mastra、Mastra Server 和 Mastra Studio。 |
| 知识库现状 | 需要建设知识库和向量检索系统，不能按“已有系统直接复用”处理。 |
| RAGFlow 条件 | 用户接受采用 RAGFlow 的方向，可以自行部署，服务器配置足够；与 Mastra 的集成仍需验证。 |
| 审批条件 | IM 没有原生审批接口，但有普通消息收发能力。用户提出通过 Bot 询问、审批人回复来完成审批。 |
| 登录现状 | 没有现成的企业 OIDC / SSO，不能假设存在统一登录系统。 |
| Bot 定制 | 希望支持 SOUL.md 等定制方式，参考 Hermes / OpenClaw 的体验，而非要求完整复刻其运行时。 |
| 开发原则 | 尽量复用现成工具，避免过度设计和重复造轮子。 |
| 工程基础 | 需要统一的日志、异常处理和必要的公共工具。 |
| 交付原则 | 最终能力全部保留，但每个阶段必须形成可供真实员工使用的端到端闭环，不建设只完成技术底座、无法实际使用的阶段。 |
| 阶段顺序 | 阶段一为企业知识问答，阶段二为文件处理与真实文件交付，阶段三为企业审批。 |
| 阶段一范围 | 仅少量真实员工通过 Bot 私聊使用；采用统一、非敏感知识集，不做细粒度知识 ACL。 |
| 阶段验收 | 使用真实 IM、真实员工身份、真实资料和真实问题，由用户人工确认是否进入下一阶段；Mock 只用于自动化验证，不作为产品可用性的唯一依据。 |
| 消息执行规则 | 同一 Bot、同一会话内保持输入和回复顺序；不同员工或不同会话可以并行。Agent 开始执行后收到的补充消息排入下一轮，不取消或重跑当前请求。 |
| Mastra 运行形态 | 阶段一中 Kairo 业务协调层与 Mastra 运行在同一 Node.js 进程，直接调用 Mastra 实例，同时开放 Mastra Server API；Mastra Studio 用于开发观察。 |
| MCP 与 stdio | MCP 是 Tool 的可选接入方式；stdio 只在出现具体 MCP 子进程工具时启用，不作为 Kairo 与 Mastra 的主通信方式。 |
| 加密文件 | Kairo 不负责解密密码保护或加密文件；识别后明确告知用户无法处理。 |

**尚不能视为已确认的内容：**独立管理后台、Web 审批、Better Auth、消息中间件、单独部署 OCR、具体后台任务队列、完整容器编排平台、群聊共享记忆模式。

## 3. 核心使用场景

### 3.1 分段提问并处理文件

员工依次发送：

```text
帮我分析一下这个月的数据
[上传销售明细.xlsx]
按部门汇总，再给我一个 Excel 文件
```

期望：系统在合理范围内将这些消息视为同一任务，识别附件与补充要求，完成计算并通过 IM 返回 Excel，而不是对每条消息分别作答。

### 3.2 查询企业知识

员工询问企业制度或操作方法。Bot 只检索该员工及当前回复场景允许访问的资料，返回答案与可辨认的来源。找不到依据时明确说明，不把推测冒充企业规定。

### 3.3 在 IM 中审批

员工提出一个需要授权的操作。Bot 将明确的审批请求发给指定审批人，审批人通过引用回复或审批编号作出决定。系统准确关联申请后，继续原任务或终止受审批限制的操作。

上述场景用于说明目标行为，不代表审批业务类型、等待时间、支持格式和交互命令已经定稿。

## 4. 功能需求

### 4.1 IM 消息接入与分段处理

**已确认目标：**理解用户分段发送的请求，并正确发送分段回复和文件。

#### 入站消息

- 保留每条原始消息的身份、发送人、会话、时间、文本、附件及引用关系，不能为了合并而丢失原始记录。
- 对重复事件和补偿消息去重，避免重复创建任务。
- 同一用户在同一会话内连续发送的文本和附件，可以聚合为一次用户输入。
- 不同用户的消息不能合并成同一个人的请求；不同会话之间不能串联附件或指令。
- 支持“先发文件、后发要求”和“先发要求、后发文件”。附件关联不明确时，不应擅自选择其他用户或其他任务的文件。
- 审批回复应先经过明确的审批识别逻辑，不能作为普通聊天片段随意合并。

**暂定职责：**Driver 上报原始消息，Kairo 业务层负责消息聚合、任务关联和调度，Mastra 处理组织好的任务输入。

**已确认规则：**不要求员工发送“完成”或“发送完毕”等命令。分段聚合使用两个全局可配置计时器：短静默窗口和最长聚合时间。短静默计时在每条普通消息到达后重新开始；最长聚合计时从本轮第一条消息开始且不重置。任一计时先到，系统就把当前内容提交为一次输入。因此正常用户停止发送后只需等待短静默窗口，不需要等待最长聚合时间；只有持续发送导致短静默不断重置时，才会触发最长上限。阶段一全局默认值确定为：短静默窗口 5 秒、最长聚合时间 60 秒；两者均允许通过受控配置调整。

Agent 已开始执行后收到的补充消息作为下一轮排队处理，不取消或重跑当前请求。

阶段一支持一个确定性控制消息 `/new`，用于立即结束旧上下文并创建新上下文。只有去除首尾空白后整条纯文本消息精确等于 `/new`，且消息不含附件时才触发；“我要开新会话”“新会话更好吗”、包含 `/new` 的普通句子或带参数的文本均不触发。该控制消息不进入静默聚合，也不交给 Agent。

收到 `/new` 后，旧上下文中所有排队但未开始的任务立即取消；正在执行的任务立即请求中止。若底层调用无法及时中止，任务完成后的文字、Tool 结果和产物均丢弃，不再向员工交付。已经完成或已经交付的任务只保留为历史记录，不删除。`/new` 之后收到的普通消息立即归入新上下文，不等待旧任务实际退出。

阶段一不提供 `/clear` 或 `/cancel`。创建新上下文与取消未完成任务都不等于删除历史数据；真实使用尚未证明需要“只取消当前任务但保留旧上下文”的独立控制消息。其他未知 `/xxx` 仍按普通消息处理。

同一 Bot、同一会话内一次只执行一个会修改该会话上下文的用户轮次，并保持任务与回复顺序；不同员工或不同会话可以并行。阶段一全局默认最多同时执行 3 个 Agent 任务，并允许通过受控配置调整；全局槽位已满时，新任务进入各自会话队列。一次 Agent Run 内相互独立的只读 Tool 是否并行，由 `tool-integration` 的安全和执行规则决定。

**仍待澄清：**阶段二的附件等待时间，以及真实使用是否会产生独立 `/cancel` 的后续需求。

IM 是否提供“正在输入”或“发送结束”信号尚未确认，因此静默聚合是可调节的工程判断，不承诺准确识别每一次自然语言输入结束。

#### 出站消息

Bot 可以按顺序发送说明文字、正文片段、图片和文件。同一任务的输出应保持可理解的顺序，避免多个任务的回复相互穿插。

同一会话已有任务执行时，新聚合形成的任务进入队列后立即且只发送一次“已收到，将在当前任务完成后处理”，不承诺预计时间或队列位置。除当前执行中的 1 个任务外，同一会话最多保留 3 个待执行任务。超过上限的新请求保留原始消息，但不创建任务，并提示员工稍后再试或发送 `/new` 取消未完成任务并开始新对话。

任务真正开始执行后，阶段一知识问答在 10 秒内完成时直接返回最终答案，不额外发送进度消息；超过 10 秒仍未完成时，只发送一次“正在查询企业知识，请稍候”提示。后续不按固定间隔刷进度，仅在完成、失败、取消等真实状态变化时通知。

文本长度限制、分段间隔及发送失败后的处理方式，按真实 IM 能力进一步确认。不要求模拟人的打字节奏。

### 4.2 Bot 人格、行为与 Skills

**已确认目标：**支持自定义 Bot 的 SOUL.md，形成可维护的人格与行为配置。

**暂定方案：**

| 内容 | 用途 |
| --- | --- |
| `SOUL.md` | Bot 的身份、表达方式、语气和交互风格。 |
| 行为规则文件，例如 `AGENTS.md` | 工作规则、业务边界和工具使用要求。 |
| `SKILL.md` 及相关资源 | 某类任务的操作方法、模板、参考资料和脚本。 |
| Bot 配置 | 模型、启用的工具及其他运行参数。 |

优先使用 Mastra 已有的配置与 Skills 接入机制，具体支持范围需验证，不另写一个通用 Skill 引擎。

人格和 Skill 内容不能改变服务端确定的员工身份、记忆隔离、知识权限或审批要求。

**阶段一已确认：**只运行一个 Bot，使用受控文件作为唯一正式配置来源；不同时建设文件和后台两套可独立修改的配置来源。阶段一至少支持 SOUL、行为规则、Skills、模型和 Tool 启用列表，并在启动或发布前完成配置校验。

**仍待澄清：**配置由谁维护、具体文件布局、修改后重启还是受控热更新、版本与回滚方式，以及何时需要多 Bot、员工级个性化或管理页面。

### 4.3 多人记忆与隔离

**已确认目标：**不同员工拥有持续且隔离的记忆。

#### 基本要求

- 以稳定的员工身份标识关联记忆，不以姓名或昵称作为唯一身份。
- 同一员工再次使用 Bot 时，可以延续已允许保留的对话上下文和个人信息。
- 不同员工的私人聊天、上传文件、长期偏好和任务状态不得相互串用。
- 用户不能通过在消息中声明另一个员工身份，切换到对方的记忆或文件。
- 若支持多个 Bot，Bot 之间是否共享某类记忆必须明确配置，不能默认共享。
- 组织架构、职位、审批权限以可信业务数据为准，不能由聊天记忆覆盖。

**阶段一已确认范围：**只保留按稳定员工身份隔离的近期会话历史与上下文，不自动提取跨天个人偏好或长期事实。近期上下文属于 `private-chat-core`，任务状态属于 `task-lifecycle`，二者均不能跨员工串用。

阶段一使用一个全局共享的“近期上下文最大空闲时间”配置项。同一员工在同一 Bot 私聊中于该时间内再次发送请求时继续现有上下文；超过该时间时自动创建新上下文。新建上下文只改变后续 Agent 输入范围，不删除原始消息、历史任务或审计记录。

空闲计时从该会话最近一次任务的最终回复成功完成交付时开始。任务仍在执行或排队时不触发上下文超时，进度通知也不重置计时。最终回复发送失败或结果未知时如何确定计时起点，归入 `task-lifecycle` 的交付异常规则继续澄清。阶段一全局默认最大空闲时间确定为 2 小时，并允许通过受控配置调整。

阶段一的上下文容量管理复用 Mastra Observational Memory，不自研压缩引擎。Observational Memory 以 `thread` 为范围，把较早对话压缩为 observations，并保留当前对话所需的近期内容。稳定员工 ID 作为 Mastra `resource` 标识，Kairo 当前上下文 ID 作为 `thread` 标识；`/new` 或 2 小时空闲超时均创建新的 thread，因此旧 thread 的原始消息和 observations 继续留作历史记录，但不会注入新上下文。阶段一不得使用跨 thread 的 `resource` 范围 Observational Memory。

Observational Memory 产生的摘要只能用于当前 thread 的对话连贯性，不能作为企业事实、员工身份、知识权限或审批权限依据；企业事实仍须重新检索 RAGFlow。Observer 与 Reflector 必须显式使用和主 Agent 相同的已批准模型，禁止回落到 Mastra 默认模型或新增第二个数据出站供应商。主 Agent 模型发生变更时，压缩模型配置必须同步校验。TokenLimiter 等裁剪能力只作为防止极端上下文溢出的安全边界，不作为主要记忆机制。

**后续实现方向：**跨 thread 的长期个人记忆继续使用 Mastra Memory 及持久化存储，不自研 Memory Engine。长期记忆单独归入 `long-term-memory` 模块，并在启用前明确写入内容、语义召回、查看、修改、清除和保留规则。

#### 群聊边界

群聊是否启用、如何触发 Bot，以及是否保留群共享历史，均待澄清。不能把“多人使用”直接等同于“所有人共享一个记忆”。

如果支持群聊，必须区分个人私人记忆和群内共同上下文。私人聊天内容不得默认注入群回答；即使提问者有权访问某份资料，也不能直接推定群内所有接收者都有权看到它。

**待澄清：**跨会话记忆范围、群聊记忆模式、长期信息保存规则、记忆查看与清除方式、保留期限。

### 4.4 企业知识库与 RAGFlow 集成

**已确认方向：**建设知识库和向量检索能力，优先采用可自行部署的 RAGFlow，并与 Mastra 集成。

**阶段一范围：**只接入一批所有试用员工均有权访问的非敏感资料，以真实问题验证检索、来源和回答质量。阶段一仍使用可信员工身份，但不实现部门或员工级知识 ACL。任何受限资料上线前，必须先完成并验证 `knowledge-acl`。

企业制度、内部流程和企业事实必须有知识来源支持；找不到可靠依据时明确拒答。通用知识可以使用模型能力回答，但必须清楚标识其不是企业资料结论。

#### 知识管理目标

支持知识资料导入、处理状态查看、更新、删除、检索测试和来源追踪。优先使用 RAGFlow 的已有能力及管理界面，不在 Kairo 中重做同类产品。

正式企业知识与员工临时上传文件应有明确边界。一次文件分析不等于自动把文件发布为企业知识。

#### 暂定集成方式

```text
员工问题
  → Mastra Agent
  → Kairo 知识检索 Tool
  → 服务端确定可访问范围
  → RAGFlow 检索
  → 返回资料片段与来源
  → Mastra 组织回答
  → IM 回复
```

暂定以 RAGFlow HTTP API 为主，MCP 不是必须项。是否使用现有 SDK、MCP 或少量 HTTP 封装，以接口覆盖度和联调结果决定。

Mastra 负责 Agent 和对话；RAGFlow 负责知识处理与检索。首期不并行维护两套 Agent、Chat 或 Memory 主流程。

#### 权限与结果要求

- 检索范围由 Kairo 根据可信员工身份和业务配置决定，不能由模型任意选择。
- 检索结果保留文档、片段或页码等实际可提供的来源信息。
- 无结果、解析失败或服务不可用时，应说明当前状态。
- 文档删除、替换或权限变更后，不应继续以旧的可访问状态提供资料；具体更新机制需验证。
- 群内回复的知识范围需要单独定义，不能只检查提问者权限。

**联调必须确认：**上传、解析、状态查询、检索、范围限制、片段读取、删除、来源映射，以及 API 凭证的实际权限边界。

**待澄清：**知识分类、维护人员、部门访问规则、Embedding 模型、重排模型、支持格式、文档规模和检索质量标准。服务器资源足够不代表这些产品决策已经完成。

### 4.5 用户文件接收与解析

**已确认目标：**能够接收员工文件，并根据任务选用合适的解析与处理方式。

#### 文件接收

先取得真实可读取的文件，再进行内容处理。文件消息卡片、文件名或一个本地路径本身，不等于服务端已经拿到文件内容。

需要验证 Driver 对不同附件是否能稳定取得内容，是否需要触发下载，以及 IM 缓存的生命周期。如果 Driver 与服务端分机部署，还需要确定文件传输方式，不能直接把一台机器的路径交给另一台机器使用。

文件进入 Kairo 后，应明确所属员工、会话和任务。一个员工的“刚才那个文件”不能关联到其他员工的附件。

#### 暂定处理原则

| 任务 | 处理原则 |
| --- | --- |
| 针对 PDF、Word、文本资料问答 | 优先复用 RAGFlow 解析与检索能力。 |
| 总结整份长文档 | 覆盖整份文档，不把少量检索命中片段当作全文。 |
| Excel 计算、汇总、筛选 | 使用表格处理库或受控执行工具，不能只依赖向量检索完成精确计算。 |
| 理解图片、图表、截图 | 根据任务使用视觉模型或 OCR，二者不等同。 |
| 临时分析附件 | 不默认发布到共享企业知识库。 |
| 正式知识入库 | 经过明确的入库操作和权限检查；是否需要审批另行确认。 |

临时文件采用何种 Dataset、存储目录或检索隔离方式属于技术方案，尚未定稿。无论采用哪种方式，都必须在服务端限制可访问文件。

**已确认边界：**密码保护或加密文件不属于 Kairo 的解密范围。系统识别后应停止内容处理，并明确告知员工文件无法处理；不得尝试绕过访问控制或要求用户提供他人的解密权限。

**仍待澄清：**具体格式及版本、文件大小和数量限制、加密文件的可靠识别方式、解析超时、临时保留期限、删除策略，以及何种情形需要用户补充指令。

### 4.6 文件生成与交付

**已确认目标：**Bot 可以根据任务返回以下类型的真实文件，而不只是回答文字或提供一段代码。

| 输出 | 目标用途 | 待确认细节 |
| --- | --- | --- |
| PDF | 报告、整理后的资料 | 版式、字体、分页、模板。 |
| Word | 可编辑文档 | 是否以 DOCX 为标准、是否需要企业模板。 |
| Excel | 可编辑表格及计算结果 | 公式、图表、格式及工作表要求。 |
| Markdown | 可保存和复用的文本资料 | 是否同时发送 IM 正文。 |
| 图片 | 图表、截图、渲染图或生成图 | 图片用途、格式及是否接入图像生成模型。 |

**暂定职责划分：**

```text
Skill：指导如何完成任务
Tool / 现成库 / 现成服务：实际生成文件
Kairo：管理产物、关联任务、安排交付
Driver：发送文件或图片到 IM
MCP：需要连接独立工具服务时使用，不是生成文件的必选条件
```

优先复用现成文档、表格、渲染和转换工具，不自行开发 Office 或 PDF 引擎。具体库与运行环境后续确定。

产物应有明确的文件类型、文件名、所属任务和交付对象。发送前至少验证文件存在、可读取，且格式与请求一致。生成失败与发送失败应能区分，不能把未交付文件报告为已交付。

**待澄清：**固定模板还是自由生成、是否允许 Agent 执行代码、是否需要独立执行容器、产物保留与再次下载方式。

### 4.7 OCR 与图片理解

**待澄清能力：**是否将扫描件和图片文字提取列入首期必需范围，以及所需识别质量。

暂定优先评估 RAGFlow 可使用的解析/OCR 能力，不自行实现 OCR。是否单独部署 OCR 服务，依据真实样本文档、数据是否可出内网及解析效果决定。

可选中文字的 PDF 不应无条件全部走 OCR；提取图片文字与理解图表、照片内容应按任务区分。

需要用真实企业样本验证扫描 PDF、中文表格、拍照文件等情况。具体引擎、部署形式和精度标准不在本版定稿。

### 4.8 组织架构与员工资料

**已确认条件：**Driver 提供组织架构接口。

**暂定方案：**将必要组织资料同步到数据库作为读取缓存，用于员工身份映射、知识权限及审批人解析。源数据仍以 IM 提供的组织信息为准，缓存不是另建一套组织管理系统。

同步应保留时间与成功/失败状态。一次失败或不完整的同步，不能直接认定员工已离职或删除其历史记录。

需要验证稳定员工 ID、部门关系、直属主管或负责人字段，以及员工 ID 与私聊会话之间的寻址关系。不能根据“经理”等职位文本让模型猜测审批人。

源数据不足时，可以暂定显式配置审批人；是否需要页面维护尚未确认。

**待澄清：**缓存字段、同步时机与周期、离职/转岗识别、缓存过期策略，以及组织变化对待审批申请的影响。

### 4.9 审批

**已确认需求：**某些企业操作需要审批。  
**优先讨论方向：**通过 IM 普通消息完成审批，不以 Web 审批或独立登录为前提。

#### 审批目标

- 受审批限制的操作，在明确授权前不得执行。
- 审批人能看清申请人、待执行动作和关键参数。
- 多条待审批申请并存时，决定能够准确对应申请。
- 申请人能知道当前等待、批准、拒绝或执行结果。
- 审批结果和实际执行结果分开记录：批准不等于执行成功。

#### 暂定流程

```text
员工提出请求
  → Agent 准备执行受审批限制的操作
  → 暂停执行并保存待审批信息
  → Kairo 根据明确规则确定审批人
  → Bot 发送审批消息
  → 审批人作出明确回复
  → Kairo 验证身份、申请和状态
  → 批准后恢复原任务；拒绝则终止相应操作
  → Bot 向申请人反馈结果
```

暂定复用 Mastra 的审批、暂停与恢复能力。Kairo 只承担企业审批规则、IM 交互、申请关联和审计，不另建通用工作流引擎。具体 API、恢复上下文和重启行为需要联调验证。

#### 候选交互，尚未定稿

```text
审批申请 AP-7F3K
申请人：张三
操作：将指定文件发布到部门知识库
文件：设备操作规范.pdf

请引用本消息回复“批准”或“拒绝：原因”。
不能引用时，请回复“批准 AP-7F3K”或“拒绝 AP-7F3K：原因”。
```

示例仅说明关联方式，不表示“知识入库一律需要审批”已被确认。

#### 防止审批错乱

审批结果由确定性代码处理，不能交给模型根据“好”“可以”等日常用语自由推断。

需要共同核对：真实发送人、指定审批人、审批编号或准确引用关系、消息所在会话、申请当前状态，以及决定是否仍然有效。审批编号只用于关联，不代替身份验证。

审批回复不应被普通消息聚合规则吞并。重复事件和重复批准不能产生重复决定；操作参数变更后，旧批准不能直接用于执行变更后的动作。

批准后的任务仍属于原申请人，不能把审批人的身份或记忆误用于恢复任务。拒绝、超时和无法确认的回复均不能被当作默认批准。

仅防止重复写入审批记录，不等于已经保证外部业务操作只执行一次。批准后恢复任务、执行结果不明和失败重试的处理，需要单独验证。

#### 需要验证的 IM 能力

能否稳定识别审批人、根据员工身份找到或打开私聊、取得引用消息关系，以及可靠记录审批通知的发送结果。

**待澄清：**哪些操作需要审批、谁审批、是否允许自审、单级还是多级、是否会签、有效期、撤销、改派、通知方式，以及一个任务暂停期间能否继续其他任务。

### 4.10 管理入口与认证

管理后台仍是候选需求，不是已确定的首期前置项目。

**暂定安排：**

| 用途 | 优先考虑的入口 |
| --- | --- |
| 员工聊天与文件任务 | 企业 IM。 |
| 审批交互 | 企业 IM，待交互规则和 Driver 能力验证。 |
| 知识维护 | RAGFlow 已有管理界面。 |
| Agent 开发与运行观察 | Mastra Studio。 |
| Bot 配置、权限映射、审批策略 | 初期可由受控配置维护，是否需要页面待澄清。 |

如果审批全部在 IM 内完成，普通员工不需要为了审批再创建一套 Kairo Web 账号。Better Auth、OIDC 和 SSO 均不作为当前确定依赖。

但 IM 已能识别员工，并不意味着 Studio、管理接口或知识后台可以匿名开放。管理入口的访问控制与员工 IM 身份是两件事，具体方式后续确定。

### 4.11 日志、异常与基础工具

Kairo 自有代码需要统一日志与异常处理约定，能够关联原始消息、会话、任务、附件和审批申请，便于判断问题发生在哪一步。

面向员工提供可理解的失败说明；技术日志保留排查所需的错误信息。避免默认将密码、凭证、完整私人对话或文件正文写入日志。

优先复用现有日志与校验库。Pino、Zod 可作为候选；不建设巨型 Utils 包、自研日志框架或独立可观测平台作为首期前提。外部服务日志以可关联任务为目标，不要求重写其内部日志系统。

### 4.12 任务生命周期

`task-lifecycle` 是 Kairo 的业务任务账本和状态协调能力，不是自研通用 Workflow Engine。它接收 `private-chat-core` 形成的输入，关联可信员工、Bot、会话、原始消息、附件、Mastra Run、Tool 调用、审批申请和最终产物。

#### 基本要求

- 任务状态必须持久化，且由确定性代码更新；Agent 的自然语言描述不能代替真实状态。
- 同一任务的输入需要版本标识。执行参数发生变化后，旧审批、旧 Tool 结果或旧产物不能自动用于新版本。
- 读取、检索等无副作用操作与外部写操作采用不同重试规则。外部结果未知时先进入对账或人工处理状态，不能直接重放。
- `/new` 会取消旧上下文中所有未完成任务并立即建立新上下文。排队任务直接取消；执行中任务请求中止；无法及时中止时丢弃其后续结果和产物，不再交付。
- 已完成或已交付任务不会因 `/new` 被删除。对于后续阶段的有副作用操作，用户取消只能阻止尚未发生的动作；已经发出的外部操作若结果未知，不能报告为已取消或已回滚。
- 任务、Tool 和产物在交付前必须再次核对所属上下文仍然有效，防止被取消任务的迟到结果进入新上下文。
- 同一会话中的新任务进入队列后立即且只发送一次收到确认，不提供不可靠的预计时间或队列位置。
- 除当前执行中的 1 个任务外，同一会话最多允许 3 个待执行任务。超过上限时不创建业务任务，保留原始消息并明确提示员工稍后再试或使用 `/new`。
- 进度通知从真实任务状态产生。阶段一任务真正开始后，10 秒内完成时不发送进度；超过 10 秒只发送一次等待提示，之后仅在完成、失败、取消等状态变化时通知。
- Mastra 可以提供 Agent Run、暂停和恢复原语；Kairo 仍负责员工、会话、业务动作、审批和交付之间的持久关联。

**阶段一最小范围：**至少区分输入聚合、排队、执行中、待交付、完成、失败、已取消和已超时，并保存每次尝试及最终回复结果。排队任务从进入排队状态开始计算，阶段一全局默认最长等待 10 分钟；超过后自动取消且不再执行，并通知员工重新发送。

知识问答从任务真正进入执行状态开始计算，阶段一全局默认执行超时为 4 分钟，并允许通过受控配置调整。超时后请求底层取消、任务进入已超时状态、迟到结果不再交付，并向员工发送可理解的超时说明。排队等待与执行超时使用两个独立计时器。

RAGFlow、模型或其他只读依赖遇到临时网络错误、限流或 `5xx` 时，同一任务最多自动重试 1 次；首次执行与重试共享同一个 4 分钟总预算，重试不会创建第二个业务任务。权限拒绝、认证或参数错误、知识无结果、用户取消等非临时结果不重试。每次尝试及最终采用的结果必须可追踪。

**仍待澄清：**完整状态集合、最终回复结果未知、重启恢复范围，以及等待审批时同一会话后续任务是否必须继续阻塞。

### 5.2 条件能力与 Agent 扩展边界

`sandboxed-execution` 是条件模块，不计入上述 19 个正式模块。只有确认允许 Agent 运行生成代码、不可信脚本或需要高风险解析器时，才建设每任务隔离的执行环境；否则文件处理优先使用确定性的受控库或服务。

`mastra-runtime-bootstrap` 是 `agent-runtime` 在阶段一中的搭建任务，不是顶层产品模块。它负责装配唯一 Mastra 实例、启动 Mastra Server、提供就绪与关闭生命周期，并让 Kairo 在同一 Node.js 进程内直接调用该实例。

Skills、Tools 与 MCP 的边界如下：

```text
SOUL / 行为规则：定义 Bot 的表达和工作边界
Skill：说明某类任务应该怎样完成
Tool：真正读取数据、计算、生成文件或执行操作
MCP：Tool 的一种连接协议，不是 Agent 主运行时
Mastra Server：Agent 长期运行和对外提供 API 的服务入口
```

人格、Skill、外部资料和模型输出均不能绕过服务端身份、知识权限、Tool 授权或审批规则。

### 5.3 组件职责边界

以下是组件职责划分，同样不代表必须拆成独立进程、服务或包。

| 部分 | 暂定职责 |
| --- | --- |
| `@kairo/driver` | IM 连接、原始消息、消息/文件/图片发送、组织数据读取；附件获取和私聊寻址能力待验证。 |
| Kairo 业务协调层 | 私聊聚合、身份映射、任务生命周期、文件与产物关联、知识权限、审批交互和输出调度。 |
| Mastra | Agent、Tool 调用、Memory，以及拟复用的暂停恢复能力。 |
| RAGFlow | 企业知识处理与检索，以及经过验证可复用的附件解析能力。 |
| 文件工具或执行环境 | 使用现成库、服务或受控脚本完成精确计算和文件生成。 |
| 持久化存储 | 保存记忆、必要业务状态、组织缓存、文件关联与审批记录；PostgreSQL 为暂定候选。 |

```text
企业 IM ⇄ Driver ⇄ private-chat-core → task-lifecycle → agent-runtime（Mastra）
                              │                │              │
                              │                │              ├─ knowledge Tool → RAGFlow
                              │                │              ├─ file Tools → 受控处理/生成工具
                              │                │              └─ side-effect Tools → approval
                              │                │
                              │                └─ 任务、审批与产物状态
                              └─ 可信员工、会话、原始消息与近期上下文
```

**阶段一运行形态已确认：**Kairo 业务协调层与 Mastra 位于同一 Node.js 进程，Kairo 通过进程内接口调用唯一的 Mastra 实例，同时开放 Mastra Server API；Mastra Studio 作为开发和运行观察入口。Kairo 与 Mastra 之间不额外建立 localhost HTTP 或 stdio 主通道。

Driver 是否与该进程同机或同进程、RAGFlow 的部署位置，以及文件如何跨机器传输仍需验证。只有这些真实边界要求持久化跨进程通信时，才判断是否需要 HTTP 通道、任务队列或消息中间件。

“容器能力”需要继续拆清：部署 Kairo/RAGFlow 服务，与让 Agent 在隔离环境执行代码，是两类需求。只有启用生成代码、不可信脚本或高风险解析器时，才启动 `sandboxed-execution` 的规格澄清；不能直接决定采用 Kubernetes 或完整 Sandbox 平台。

## 6. 基本质量要求

| 方面 | 要求 |
| --- | --- |
| 隔离 | 员工身份、私人记忆、临时文件和知识权限在服务端约束，不只依赖 Prompt。 |
| 可恢复 | 记忆和待审批状态需要持久保存。重启后的恢复范围与方式在验证后明确。 |
| 防重复 | 重复消息、重复审批和不确定的发送结果不能被简单当作新任务反复执行。 |
| 结果准确性 | 表格计算使用可验证的计算过程；全文总结不能仅覆盖检索到的少数片段。 |
| 用户反馈 | 文件解析、等待审批、任务失败等状态应可理解，避免长时间无响应或持续刷屏。 |
| 可追踪 | 能从一条用户请求追踪到文件处理、审批决定和最终输出。 |
| 可维护 | 通用能力使用现成组件，业务代码集中在必要的衔接点。 |

具体并发数、响应时间、单文件上限、保留期限及恢复时限，本版不设未经确认的数字。

## 7. 分阶段范围

### 7.1 交付与放行原则

最终愿景保留能力地图中的全部正式模块，但按真实端到端闭环逐阶段交付。每个阶段都必须使用真实 IM、真实员工身份、真实资料或文件进行验证；Mock、单元测试和接口模拟只用于自动化保护，不能代替产品可用性验证。

是否进入下一阶段由用户根据持续真实使用人工确认，不以“一次演示成功”作为放行依据。当前不预先设置未经验证的固定准确率、并发量或响应时间数字。

### 7.2 阶段一：企业知识问答

阶段一包含 `im-transport` 的必要能力验证，以及 `private-chat-core`、`task-lifecycle`、`agent-runtime`、最小 `bot-customization`、最小 `tool-integration`、`knowledge-management`、`knowledge-qa` 和贯穿式 `operability`。

阶段一仅面向少量真实员工私聊，使用统一、非敏感知识集。员工身份必须可信，近期上下文必须按员工隔离；不包含细粒度知识 ACL、长期个人记忆、群聊、文件任务或审批。

阶段一首个自定义 Tool 是只读知识检索 Tool。`mastra-runtime-bootstrap` 作为 `agent-runtime` 的首个搭建任务，必须在真实知识问答闭环前完成。

### 7.3 阶段二：文件处理与交付

阶段二包含 `file-intake`、`document-processing`、`spreadsheet-processing`、按样本门控的 `image-processing`、`artifact-lifecycle`，并扩展 `tool-integration` 和 `task-lifecycle`。

阶段二先选择一种真实文件任务形成“接收文件—实际处理—返回可打开文件”的闭环，再逐步扩展格式和处理类型。密码保护或加密文件只检测并拒绝，不解密。

### 7.4 阶段三：企业审批

阶段三包含 `organization-policy` 和 `approval`，并扩展 `task-lifecycle`、`tool-integration` 与 `operability`。审批必须绑定至少一个真实受控业务操作，不能使用无业务效果的 Mock 操作完成验收。

审批决定与实际执行结果必须分别记录；已批准不等于已完成。

### 7.5 后续与条件门禁

- `knowledge-acl`：任何受限企业资料上线前必须完成，不受固定阶段编号限制。
- `long-term-memory`：在近期上下文稳定后单独澄清和验收。
- `group-chat`：在知识 ACL、群受众权限及 Driver 群聊能力验证后最后启用。
- `sandboxed-execution`：只有确认允许 Agent 运行生成代码、不可信脚本或高风险解析器时才立项。
- 完整 Bot 动态配置、多 Bot、员工级个性化及管理页面，在出现真实维护需求后扩展。

### 7.6 当前不预先建设

不因“将来可能需要”而提前建设多 IM 通用框架、完整 Web 管理后台、自研 Agent/Memory/Workflow 引擎、自研知识库/OCR/文档渲染引擎、复杂多租户平台或容器调度平台。

NATS、pg-boss、Redis、Better Auth、独立 OCR、MCP Server、对象存储和 Sandbox 等都属于具体需求明确后的候选，不因前文讨论过就视为已批准选型。

本版仍不拆开发 Ticket、不给出开发排期。阶段一模块规格和真实接口验证完成后，再进入计划与任务拆分。

## 9. 候选验收场景

以下场景用于校准目标。每个阶段的自动化测试之外，还必须通过真实 IM 和真实用户任务验证；是否进入下一阶段由用户人工确认。涉及后续或条件模块的场景，不能直接当作阶段一承诺。

| 场景 | 期望结果 |
| --- | --- |
| 两个员工在不同私聊中同时提问 | 两个会话可以并行处理，身份、上下文、任务和回复不串用。 |
| 同一员工分段发送一条知识问题 | 系统在短静默后自动聚合，不要求员工发送“完成”。 |
| Agent 已开始处理后员工补发消息 | 当前请求不取消、不重跑；补充消息排入下一轮并保持回复顺序。 |
| 员工询问企业事实但知识库无可靠依据 | Bot 明确说明没有企业资料依据，不把模型推测写成企业规定。 |
| 员工询问可由模型回答的通用问题 | 可以回答，但清楚标识内容来自模型通用知识而非企业资料。 |
| 一个员工连续发送文本、附件、补充要求 | 在阶段二约定的聚合和附件等待规则内形成同一任务，不漏掉补充要求。 |
| 两个员工交错发送消息和文件 | 身份、附件、任务和回复不会串用。 |
| 员工 A 向 Bot 提供私人信息，员工 B 随后提问 | B 的回答中不会出现 A 的私人记忆。 |
| 群聊请求涉及私人记忆或受限资料 | 不因提问者有权限而向整个群泄露。 |
| 用户要求总结整份长文档 | 处理范围覆盖全文，而不是只总结少数命中片段。 |
| 用户要求对 Excel 汇总并导出 | 结果经过实际计算，返回可打开的 Excel 文件。 |
| 用户要求 PDF、Word、Markdown 或图片文件 | 返回对应真实文件；生成和交付失败时准确说明状态。 |
| 某员工上传临时文件，另一员工发起检索 | 后者不能检索到前者的未授权文件。 |
| 同一审批人同时收到两条申请 | 每次回复只影响明确对应的申请。 |
| 非审批人或重复消息回复“批准” | 不能越权批准，不能因此重复执行操作。 |
| 任务获批后执行失败 | 不将“已批准”误报为“已完成”，保留可追踪状态。 |
| 服务在等待审批时重启 | 在验证后的恢复机制下，申请与原任务仍可正确关联。 |

## 10. 当前结论

产品方向是：**以单一企业 IM 为入口，使用 Mastra 承担 Agent 能力、RAGFlow 承担知识能力，Kairo 通过 19 个正式能力模块聚焦消息、任务、身份、Tools、知识、文件、记忆隔离和企业审批之间的衔接。**

交付顺序已经确认：**阶段一企业知识问答，阶段二文件处理与真实文件交付，阶段三企业审批。**每个阶段必须形成真实员工可使用的端到端闭环，并由用户人工确认是否进入下一阶段。

下一步不是立即拆开发 Ticket，而是先完成阶段一模块规格。优先澄清 `private-chat-core` 与 `task-lifecycle` 的输入、状态、不变量和失败行为，再验证 Driver 与 Mastra/RAGFlow 的真实接口。
